## The two skills that cover the output you edit

A skill is a markdown file with a `name` and a `description`; Claude Code loads its full
contents when a task matches that description. These two cover the half of a run that
arrives with work attached — `flawless-unit-browser` for the specs `unit-browser` and
`perf-harness` write, `flawless-findings` for the three tasks that write no code and only
report. Both ship in `.claude/skills/` in the tool's own repository.

## `flawless-unit-browser`

**Loads when** a generated unit or browser spec is red, when you are filling TODOs after a
run, or when a browser spec reports `unknown component`. Its description also names its
contents — what the specs assert, the provider wrapper and its write-once fixtures, the
mock allowlist, `test.skip` and `TODO(flawless)` markers, hand-hardening colocated specs,
registering components in the browser host — so naming any of those pulls it in.

**What it knows.** `unit-browser` writes Vitest + Testing Library specs from static
analysis; with `perf-harness` also selected you get Playwright browser specs that mount
through the profiling host. Everything asserted was *derived*: the specs describe the render
at the props they pass, never the last `return` in the body.

```bash
flawless-react "src/**/*.tsx" --tasks unit-browser,perf-harness --colocate --no-interactive
```

### Fixtures are written once, and an empty cast is a vacuous pass

Unit specs mount inside `flawless/provider.tsx`, derived from the layout's JSX chain around
`{children}`. That file regenerates; the values live in `flawless/provider.fixtures.ts`,
**written once and never again — not even with `--force`**.

Filling it is the highest-value hardening move. Replace the emitted empty cast in
`initialState` (or whatever the layout passed) with a real seeded shape mirroring your app's
seed data, so specs mount the way the app renders: authenticated, themed, populated.

```ts
initialState: {
  user: { id: "…", email: "trustee@demo.local", name: "…", /* seed persona */ },
  status: "authenticated",
} satisfies ComponentProps<typeof StoreProvider>["initialState"],
```

Pin any timestamp; `Date.now()` in a fixture makes specs nondeterministic. And tighten the
assertion as you fill: a mocked building named `"flawless-name"` must reach the DOM
(`expect(screen.getByText("flawless-name")).toBeInTheDocument()`), or the spec passes
rendering an empty state — the vacuous pass this tool exists to prevent.

### The mock allowlist is closed

Client specs mock only `next/navigation`, `next/headers`, `server-only`, `next/link`,
`next/font/*`, and `"use server"` modules. Do not widen it: mocking a UI component replaces
the element the interaction tests click. Never mock `cn` or `clsx` away entirely — classes
vanish. One wart, fixed in **FR-027** but alive in older suites: a spec importing `cn` from
a utils module may carry an async stub for a sync function,
`vi.mock("@/lib/utils", () => ({ cn: vi.fn(async () => ({})) }))`. Regeneration emits the
sync form; in place, use a sync join so classes stay legible.

```ts
vi.mock("@/lib/utils", () => ({
  cn: vi.fn((...args: unknown[]) => args.filter(Boolean).join(" ")),
}));
```

### Skips and TODOs are answers waiting, not defects

A `test.skip` with a named reason is intended output. Never delete the assertion or
hand-write one — give the component what the reason asks for (a `data-testid`, a fixture)
or extend the generator. `TODO(flawless)` markers come in three kinds:

- **"some return shapes could not be inferred."** The tool already tried the dep's own
  declaration — a `Promise<T>` annotation, or a single-fetch body joined to the OpenAPI
  example, which emit an `/* inferred from … */` fixture and no TODO. The marker means usage
  *and* declaration came up empty: a computed return, a generic, a dotted callee
  (`db.query.findMany`), an unannotated factory (`getDb`), a `cache()`-wrapped export the
  function mapper cannot unwrap, or a type hitting a construct zod inference bails on
  (`.transform`, a union, a record, a date) — barrel-resolved workspace types work since
  **B-8** and `z.infer` enums and objects since **B-9**, so a survivor left the supported
  subset. Give the mocked data-dep a realistic resolved value; where every consumer of the
  handle is itself mocked, an opaque `{}` *is* right — say so in a comment replacing the
  TODO.
- **"wrap renderTarget() in the matching Root."** The tool does this itself when the part's
  own file exports the family (a Root-rendering sibling plus a Content sibling) and the
  family is open-state, so it survives only for rootless files, cross-file families, or
  value-driven ones (accordion, tabs). Mount the part inside its Root as call sites do —
  `render(<AlertDialog><AlertDialogTrigger>Delete</AlertDialogTrigger></AlertDialog>)` —
  then assert its content. Dialog-family parts need the content wrapper too
  (`<Dialog open><DialogContent>…`), and portal content is read off `baseElement`.
- **"server action stubbed — give it a realistic return value."** The tool does this itself
  when the action returns a single literal, redirect and notFound exits discounted; the
  marker survives only where inference bailed — computed returns, two distinct shapes, an
  unresolved sibling export. Read the action, pick the shape the component consumes, write
  it into the stub.

### The colocated stamp, and where hand-hardening is safe

Colocated specs (`--colocate`, written as `<file>.flawless.test.tsx` beside the source) are
kept on re-runs, and their first line is a provenance stamp —
`// @flawless-generated sha256:<hex16> flawless-react@<version>`, hashing the rest of the
file. `--force` rewrites a spec only while that stamp matches; hand-harden one and the
mismatch protects it, kept and listed in the summary as hand-edited.

Leave the stamp line alone: deleting it does not make the file regenerable, it demotes it to
pre-stamp. The body edit already marks the file as yours, and deleting the whole file is how
you hand a spec back. Specs inside the out dir are rewritten on any re-run — never
hand-harden those, colocate first.

Run them with `bun run flawless:unit`; the emitted Vitest config selects both
`src/**/*.flawless.test.*` and `flawless/unit/**`. A project script that is a bare
`bun test` collects colocated specs under the wrong runner — scope it to `bun test tests`.

### The browser host registry, and `unknown component`

Browser specs mount through `flawless/host/` and exist only when both `unit-browser` and
`perf-harness` ran. The mount tables `REGISTRY`, `FN_PROPS` and `WRAP_IN` live in
`host/registry.ts`, which **regenerates on every run** — a newly analysed component arrives
by a plain no-force re-run, nothing to hand-edit. Write-once `host/main.tsx` is only the
wrapper (polyfills, provider, MSW, profiling machinery); components you register by hand go
in its spreads, which survive regeneration:
`const ALL = { ...REGISTRY, MyComponent: MyComponent as unknown as Component }` — the cast
is required, since a strict tsconfig rejects a props-typed component in a
`Record<string, Component>` — plus `ALL_FN_PROPS` and `ALL_WRAP_IN` for function-prop stubs
or a wrapper chain.

So `unknown component: <Name>` reads two ways. On a current suite the re-run has not
happened: re-run the tool. On a pre-split suite — a `main.tsx` with no `from "./registry"`
import — take the one-time migration the run's warning names: delete `host/main.tsx` and
re-run, regenerating the provider wiring from `--provider`, or port the hand wiring into a
wrapper importing `./registry`. No flag rewrites `main.tsx`; write-once is absolute,
`--force` included. This was findings-ledger **FR-016**, fixed by the split.

## `flawless-findings`

**Loads when** you are triaging a findings list after a run, deciding fix-versus-suppress,
or a suppression shows up as "unused". It advertises perf-static, a11y and react-rules
findings, REPORT.md's accounting, the `reports/` JSON and sidecars, and the suppression
rules that keep your project's Biome and the tool's sweeps agreeing.

**What it knows.** Three tasks only report: `perf-static` runs the tool's own rules, `a11y`
and `react-rules` are Biome sweeps with narrowed rule sets. Findings print as
`file:line:col rule message` and land in `flawless/reports/*.json` — one aggregate per task
plus per-component files, written **only for components that own findings**, so stale
per-component reports from earlier runs linger. Trust the task summary counts, never a glob
over `reports/`.

`REPORT.md` regenerates every run and describes the **last run, not the suite on disk**. Its
components table accounts for every component in exactly one render-mode row (client, rsc,
compound-part, document-root, null) split by mountable or not; "Not covered, and why" names
each gap; the task table records what that run wrote, with a Status column for where
`perf-harness` sat in the lifecycle — generated, refreshed or kept. A file count is not
coverage.

### Triage in order, and stop before the advisory tail

1. **`perf/set-state-in-render`** (error) — always real, fix first.
2. **Hook dependencies.** `hook-extraneous-dependency` usually means the dep is never read:
   remove it, or for a scroll-on-change effect make it real by reading it
   (`if (messages.length === 0) return;`). For `hook-missing-dependency`, wrap the function
   in `useCallback` and add it rather than suppressing.
3. **`perf/unstable-child-prop`** — a real win when the receiving child is memoised or heavy
   (a third-party `<Sonner>`, a memo'd list). Hoist static objects and arrays to module
   scope; leave inline arrows to plain DOM elements alone.
4. **`noArrayIndexKey`** — real for editable lists: add a client-side id at creation, key on
   it, strip it at submit. A reasoned suppression for server-static lists, or where the
   index *is* the domain identity.
5. **`perf/unresolved-prop`, `no-memoisation-with-children`, `missing-memo-leaf`** —
   advisory scale. Fix where profiling agrees; chasing them to zero is churn, not
   performance.

### A suppression is an answer — and it can be "unused" on the other side

Every suppression carries its reason, and none exists to make a batch green.

```tsx
// biome-ignore lint/a11y/noLabelWithoutControl: generic wrapper — every call site associates the control
```

Placement matters, because Biome attaches the comment to the next line's diagnostic: for a
multi-line JSX element whose finding anchors on the `key=` attribute, it goes inside the tag
directly above that attribute, not above the element.

Then the **cross-config trap**. The tool's sweeps run a scratch config holding only their own
rules; your project's Biome has its own set, and a rule enabled in only one of the two makes
the suppression "unused" in the other. The tool's side is handled — the sweeps ignore
`suppressions/unused`. Yours is not: if the project config does not enable the rule you are
suppressing, your own `biome ci` flags the comment. Enable that rule in the project config —
usually free, since the suppressed site was the only finding — and both runs agree the
suppression is legitimate.

Finally, track the ledger across runs (the skill's worked example: perf-static 246 / a11y 1
/ react-rules 10) and explain every delta. A burn-down commit should be able to say
"a11y 1&#8594;0, react-rules 10&#8594;0" with one cause per line. New findings after a
regeneration are usually the analyser seeing new components, not regressions — check the
components count first.

## Installing them

Plain directories, no dependencies. Copy them out of the tool's repository into project
scope (checked in, shared with the repo) or user scope (every project on this machine);
project scope wins when both exist.

```bash
mkdir -p .claude/skills
cp -R /path/to/flawless-react/.claude/skills/flawless-{unit-browser,findings} .claude/skills/
cp -R /path/to/flawless-react/.claude/skills/flawless-{unit-browser,findings} ~/.claude/skills/
```

**A stale copy is worse than none.** The repository copy is the source of truth and moves
when the tool moves — the `cn` async stub is fixed as of FR-027, the registry split as of
FR-016, and two of the three `TODO(flawless)` kinds are now filled in automatically in cases
that once emitted a marker. A copy predating those loads with exactly the same confidence as
a current one, and is wrong in the situation you reached for it. Re-copy after every upgrade,
and if you keep both scopes, diff them.
