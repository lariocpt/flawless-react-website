## Usage

```text
flawless-react <entry-or-glob> [options]
flawless-react                       (interactive menu)
```

The positional is a `.tsx` file path or a glob such as `"src/**/*.tsx"`. Each matched file is analysed as its own entry component and runs against every selected task.

Resolution is deliberately simple: if the positional resolves to a path that exists, that single file is the entry. Otherwise it is treated as a glob relative to the current directory — and a value with no glob characters that does not exist on disk matches nothing, so the run stops with `no files matched`.

Run with no positional in a TTY and you get the interactive menu instead: a prompt for the path or glob, a prompt for the output directory, and a checkbox list of the seven tasks with `perf-harness` and `perf-static` preselected. `--no-interactive` disables that path entirely, in which case a positional and `--tasks` are required.

## Options

Every flag that takes a value accepts both `--flag value` and `--flag=value`. An unrecognised `--flag` is an error rather than a silently ignored argument.

| Flag | What it does |
| --- | --- |
| `--out <dir>` | Output directory for everything the run writes. Defaults to `./.flawless`. In `--nextjs` mode it defaults to `<nextRoot>/flawless/` instead. |
| `--tasks <csv>` | Comma-separated task ids to run, skipping the interactive menu. An unknown id is a hard error that prints the list of valid ids. |
| `--no-interactive` | Never prompt. Requires a positional and `--tasks`. |
| `--run-tests` | After generating, run the produced test suites. |
| `--no-inline-summary` | Do not drop a `<Component>.flawless.json` next to each source file. |
| `--json` | Print a machine-readable JSON summary — the resolved `outDir` plus the full per-task results — to stdout. |
| `--nextjs [<path>]` | Treat `<path>`, or the current directory when the value is omitted, as a Next.js project: detect the router style, emit MSW handlers and swagger from `app/api` or `pages/api`, auto-set the app resolver from `app/layout.tsx` or `pages/_app.tsx`, merge the generated deps into the project's `package.json` as `devDependencies`, and place everything under `<nextRoot>/flawless/`. |
| `--app-resolver <file>` | Override the auto-detected Next.js app resolver. It is an alias for `--provider` in Next.js mode, and the file must default-export a wrapper component. |
| `--swagger-url <url>` | Fetch an OpenAPI spec from a live URL, for example `http://localhost:3000/api/docs` from next-swagger-doc, and prefer it over static AST inference. In `--nextjs` mode that default URL is tried automatically with a short timeout; pass `--swagger-url` to force a specific URL, or `--swagger-url=off` to skip the auto-try. |
| `--depth N` | Levels of locally-imported child components to follow. Default `3`. `0` analyses the entry component only. Must be `>= 0`. |
| `--variants N` | Variant rows generated per component. Default `5`. Must be `>= 0`. |
| `--include-children` | Walk transitive child components. On by default; pass `--include-children=false` (`=0` and `=no` also work) to skip. |
| `--props '<json>'` | A JSON object merged over the synthesised default props of the first entry. Use it when a prop's type could not be resolved. |
| `--provider <file>` | Path to a `.tsx` file that default-exports a wrapper component. The host renders every mounted component inside it — this is how Redux, React Query, theming, or any other context-based store gets threaded through. |
| `--api <spec>` | Path to an OpenAPI / Swagger JSON or YAML file. Scaffolds a standalone Bun mock server (`mock/server.ts`) with static route handlers generated from the spec's first example responses; the host server transparently proxies all non-asset requests to it. |
| `--force` | Overwrite an existing output directory. |
| `--report` | Emit `scripts/report.mjs`, so `bun run report` aggregates run output into a markdown summary. |
| `-h, --help` | Print the help text and exit. |
| `-V, --version` | Print the version and exit. |

## Tasks

The seven task ids are exactly these. Anything else — including plausible-looking transpositions such as `static-perf` — is rejected by `--tasks`.

| Task id | What it emits or reports |
| --- | --- |
| `perf-harness` | Scaffolds the standalone performance suite into `<outDir>/`: `host/` (Bun server, bundle, `window.__profile` driver), `playwright.config.ts`, `tests/<Component>.profile.spec.ts` for every analysed component, `budgets.json`, and `heaps/` for the V8 snapshots written at test time. Measurement is React's built-in `<Profiler>` for `renderCount` / `renderTime` and react-scan for unnecessary rerenders. Produces files, not findings. |
| `unit-browser` | Scaffolds Vitest units at `unit/<Component>.test.tsx` (jsdom + `@testing-library/react`) and Playwright functional specs at `browser/<Component>.spec.ts`, along with `vitest.config.ts`, `setup.ts`, and `browser/playwright.config.ts`. Outside Next.js mode it also merges `test:unit`, `test:perf`, and `test:browser` scripts plus the matching dev deps into the suite's `package.json`. Produces files, not findings. |
| `perf-static` | Reads the parsed tree — no browser, no build — and writes `reports/<Component>.perf-static.json`. Two rules fire: `perf/no-memoisation-with-children`, when a component renders three or more child components and uses none of `useMemo` / `useCallback` / `memo` / `useRef`, so every parent rerender rerenders all of them; and `perf/unresolved-prop`, when no default could be synthesised for a prop and the generated tests will pass `undefined`. |
| `a11y` | Runs biome's accessibility rules over the entry file and every walked child, then writes `reports/<Component>.a11y.json`. Findings are filtered to the `lint/a11y` category, so correctness rules do not leak into an accessibility report, and each one carries file, line, column, rule, and severity. |
| `react-rules` | Runs a curated set of bug-catching React and hooks rules through biome — `useExhaustiveDependencies`, `useHookAtTopLevel`, `useJsxKeyInIterable`, `noArrayIndexKey`, `noChildrenProp`, `noVoidElementsWithChildren` and friends — and writes `reports/<Component>.react-rules.json`. The config is supplied by flawless-react, so the project's own `biome.json` is bypassed and the rule set is the same on every machine. |
| `e2e` | Emits `e2e/` — a Playwright config pointed at the target's real dev server (overridable with `FLAWLESS_E2E_BASEURL`), a `global-setup.ts` stub for login, and one spec per app-router page asserting the route loads with no console or page errors, plus up to three interactions harvested from that page's component tree. Next.js mode only. |
| `load` | Emits `load/` — crust pipes per route and per API operation, run with `bun run flawless:load`. Baselines are written on the first run and compared on later ones. |

Selecting nothing leaves the run with `perf-harness` alone. Task order on the command line is the order they run in, and each task's findings are printed as they complete.

### Task availability and biome

`perf-harness`, `unit-browser`, `perf-static`, `e2e` and `load` are self-contained and work anywhere. `a11y` and `react-rules` shell out to biome, which the standalone binary cannot carry inside itself, so it is looked for in three places in order: this package's own `node_modules/.bin/biome`, then `node_modules/.bin/biome` in the project being scanned, then `biome` on `PATH`. If none of the three hits, both tasks fail with a message naming the paths that were tried.

Any React codebase that already lints with biome satisfies this for free. Otherwise, add it to the project you are scanning:

<InstallBlock command="bun add -d @biomejs/biome" label="Add biome" />

Or install flawless-react from the source package, which carries `@biomejs/biome` as a real dependency so all seven tasks work with no further setup. That channel needs Bun >= 1.1 on the machine running it.

<InstallBlock command="bun add -g flawless-react --registry https://npm.in.drlario.org" label="Install" />

## Output and reporting

Beyond whatever the selected tasks write, every run produces:

- `<outDir>/reports/summary.json` — a timestamp plus, per task, its id, ok flag, one-line summary, output count, finding count, and error if it failed.
- A `<Component>.flawless.json` next to each analysed source file, unless `--no-inline-summary`. It holds per-task finding counts, the three highest-severity findings, and paths to the full `a11y`, `react-rules`, and `perf-static` reports. This is what makes issues surface where the code lives rather than only in a terminal that has scrolled away.

Findings are printed grouped by file, one line each as `severity  line:column  rule  message`, followed by a summary table with a status, file count, and finding count per task.

## Running the generated tests

`--run-tests` runs the suites after generation. It only fires when `perf-harness` or `unit-browser` was selected and no task failed, and in an interactive run you are asked to confirm instead. It runs `bun install` in the output directory first if `node_modules` is missing, then `test:unit`, `test:perf`, and `test:browser` as the selected tasks warrant, and prints which suites failed.

## Exit codes

| Code | Meaning |
| --- | --- |
| `0` | Every selected task succeeded. |
| `1` | At least one task failed or threw. |
| `2` | Usage error: a bad flag or flag value, no positional and no interactive TTY, no files matched the glob, or nothing analysable was found. |
