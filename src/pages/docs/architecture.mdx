## Overview

`flawless-react` is structured as a task registry. The CLI (`src/cli.ts`) parses args — or prompts for them — expands the positional glob into entry files, analyses each one into a `ComponentTree`, then dispatches the selected tasks against a shared `RunContext`.

Each task under `src/tasks/` is self-contained. They share the analyse output and write their own slice of the output directory (`profile/`, `unit/`, `browser/`, `e2e/`, `load/`, `reports/`).

```
                 entry.tsx
                     │
                     ▼
        ┌─────────────────────────┐
        │        analyse/         │   TypeScript compiler API
        │  parseFile  ─►  imports │
        │       │                 │
        │       ▼                 │
        │  extractProps           │   → propsShape + variants + unresolvedProps
        │  extractHooks           │   → ["useState", "useEffect", …]
        │  walkChildren           │   → recursive ComponentTree (cycle-guarded)
        └────────────┬────────────┘
                     │
                     ▼
                ComponentTree
                     │
                     ▼
        ┌─────────────────────────┐
        │        scaffold/        │
        │  templates ─► RenderedFile[]
        │  index    ─► Bun.write   │
        └────────────┬────────────┘
                     │
                     ▼
              <outDir>/ on disk
```

## Phase 1 — analyse

Implemented under `src/analyse/`, one file per responsibility. The pieces are kept small enough to swap out individually if you later want to use a different parser (SWC, for instance).

### parseFile.ts

Reads the entry file and runs `ts.createSourceFile(…, ScriptKind.TSX)`. Two recognisers run in order:

1. **`tryReactFCDecl`** — matches `const X: React.FC<Props> = (props) => …`, including the `FunctionComponent` alias and the directly-imported `FC<Props>` form. It captures `componentName`, the body node, and the props `TypeReferenceNode`.
2. **`tryDefaultExportFn`** — matches `export default function X(props: Props) { … }`.

If neither matches, the function throws with a descriptive message. The recogniser is deliberately small so the rules stay legible.

`parseFile` also returns an `imports` map of local name to module specifier, so child resolution can look up where a JSX tag came from.

### extractProps.ts

Walks the resolved `InterfaceDeclaration` or `TypeAliasDeclaration`. Same-file types resolve directly; imported ones are chased two hops through `resolveModule`, with a parse cache so a shadcn-style layer does not re-read the same file dozens of times. For each `PropertySignature`, the type node is mapped:

| Source type | Default | Variants |
| --- | --- | --- |
| `string` / `number` / `boolean` / `null` | `""` / `0` / `false` / `null` | — |
| `T[]` | `[]` | — |
| inline `{ a: string; … }` | recurse | — |
| `"a"` / `42` / `true` (literal) | that literal | — |
| `"a" \| "b" \| "c"` (union of literals) | first literal | all literals become variant rows |
| anything else | — | added to `unresolvedProps` |

The variant matrix is **pairwise, not cartesian**: for each union prop, one row is generated per literal with every other prop left at its default. That keeps `--variants` honest as a row count rather than a combinatorial estimate.

### extractHooks.ts

Visits the component body's descendants once. Any `CallExpression` whose callee identifier matches `/^use[A-Z]/` is collected — both the bare `useState()` and the namespaced `React.useState()` forms. The result is deduplicated and sorted.

The list is **informational**. It appears in the generated spec's output but does not yet drive different rerender strategies. Hook-aware rerender drivers — calling a specific `useState` setter, say — are a sensible future enhancement.

### walkChildren.ts

Walks the JSX in the component body and collects `JsxOpeningElement` and `JsxSelfClosingElement` tag names that:

1. Start with an uppercase letter, so components rather than DOM elements, and
2. Resolve to a *locally-imported* module — the import specifier starts with `./`, `../`, or `/`.

Bare specifiers such as `react` or `lodash` are ignored. The resolver tries `<path>`, then `<path>.tsx`, `<path>.ts`, `<path>/index.tsx`, and `<path>/index.ts`, so `./Foo`, `./Foo.tsx`, and `./Foo/index.tsx` all work.

### index.ts — the orchestrator

Recursively analyses each discovered child up to `--depth`, cycle-guarded by absolute path. If a child file cannot be parsed because it holds no recognisable component, it is skipped silently: composite trees often pull in non-component utilities. Other parse errors propagate.

The output is a `ComponentTree`:

```ts
type ComponentTree = { entry: ComponentInfo; children: ComponentTree[] };
type ComponentInfo = {
  componentName: string;
  filePath: string;
  importSpecifier: string;
  propsShape: PropsShape;
  variants: PropsShape[];
  hooks: string[];
  unresolvedProps: string[];
};
```

## Phase 2 — scaffold

Implemented under `src/scaffold/`.

### templates.ts

A pure function: `renderSuite({ tree, outDir, variants, report }) → RenderedFile[]`, where each `RenderedFile` is `{ relPath, content, executable? }`. There is no file IO here, which keeps the templates trivially testable.

The flat list of components — root plus recursed children, deduped — becomes:

- One **import line per component** in `host/main.tsx`, with the path expressed relative to the host directory.
- One entry in the `REGISTRY` object keyed by component name, so `window.__profile.mount(name, props)` can find them.
- One **spec file per component** at `profile/<Name>.profile.spec.ts`. Each spec bakes its defaults, variants, and hooks list in as literals — no shared fixture file, no implicit coupling.

The host page initialises `react-scan` once at module load, buffers any "unnecessary rerender" events into `scanEvents`, and exposes `mount`, `rerender`, `unmount`, `getRenderInfo`, and `getScanEvents` on `window.__profile`. The driver API is deliberately small.

### index.ts — the writer

Resolves `outDir`, refuses to overwrite unless `--force`, creates the directory tree with `fs/promises.mkdir({ recursive: true })`, and writes each `RenderedFile` with `Bun.write`. The `executable` flag flips a `chmod 0o755` on emitted scripts.

## Why two phases

The split buys three things:

- **Test analysis without producing files.** Most unit tests operate on the `ComponentTree` directly, with nothing written to disk.
- **Test rendering without touching disk.** `renderSuite` returns an array, so the scaffold tests assert on the in-memory result before the integration tests round-trip through `Bun.write`.
- **Swap either side independently.** A future SWC-based analyser only has to produce a `ComponentTree` and the scaffolder is unchanged. A future scaffolder that emits a Vitest suite instead of a Playwright one only consumes the tree.

## What is intentionally absent

These are limits by design, not gaps waiting to be filled.

- **No runtime.** The CLI never imports React or Playwright. It does not boot a server. It only reads and writes files.
- **No type checker.** The analyser runs `ts.createSourceFile`, not the full TypeScript program. Imported types are not resolved across files. That trades accuracy for speed and for requiring zero project configuration.
- **No code generation framework.** Templates are string concatenations. Easy to read, easy to diff against the generated output, easy to grep.

If a future feature needs cross-file type resolution — resolving a `Props` type imported from a sibling file, for example — the right path is to create a `ts.createProgram` lazily in `extractProps` for that one resolution, not to bring in a heavier framework.
